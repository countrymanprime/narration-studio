# feature-cleanup

## Why this exists

Once tests are green, work tends to get called "done" — but code left behind by the change (an unused helper, a stale doc paragraph, a debug print, an untracked scratch file) accumulates and becomes the next feature's silent landmine. This skill is the last pass that catches it while the change is still fresh in context, instead of leaving it for someone else to trip over later.

## When to use this

After `full-verification-gate` has passed (or its required manual-verification step is explicitly confirmed), before the change is committed or reported as finished.

## What to do

1. **Re-verify after cleanup, not before.** Any edits made during this pass (removing code, editing docs) can themselves break something — after making cleanup edits, re-run `full-verification-gate` once more before finishing.
2. **Dead code check.** Run `pnpm knip` (it is part of `pnpm check` too): it finds unused files, exports and dependencies across `apps/ui`, `scripts/` and `tools/`, and it is gated at zero, so any finding is from this change. Fix it (delete the code, or drop the `export`), or add an entry to `knip.jsonc` with a written reason; never add an ignore just to quiet it. Knip does not read Go, Python, Lua or docs, so for every symbol removed from a call site there, still grep the repo to confirm nothing else references it, and for every new Go/Python/Lua function confirm it is actually called somewhere.
3. **Scratch artifacts.** Confirm nothing untracked and unintentional is left behind: stray `console.log`/`print` debug statements, `.test-tmp-*` directories, `apps/ui/screenshots/` or `test-results/` content (these are gitignored scratch output, not deliverables — don't commit them, and don't leave large stale runs lying around either).
4. **Docs staleness.** Run `doc-impact-check`: it maps the diff to the docs the change owes (utilities, workflows, architecture, guides, threat model) and has you update them or write `Docs: none — <reason>` in the PR description. Then run `doc-unslop` on the Markdown you touched, following `docs-style`. If `apps/ui` changed, `doc-impact-check` also sends you to `doc-screenshot-sync`.
5. **Decision bookkeeping.** If the change embodied a real decision (not just an implementation detail) that should be durable, use `adr-author` to record it now that the code has landed — that skill's own rule is to write the ADR after the change, not before.
6. **Design-system contradiction check.** If the change touched `apps/ui/src/components/primitives/` or `apps/ui/src/styles.css`, run `design-spec-guard` to confirm nothing was silently reverted against a recorded ADR.
7. **Trust-boundary and diagram check.** If the change alters what crosses a trust boundary or what the app sends off the machine (a download or its catalog, the app's own update, a sidecar's arguments or output, the REAPER bridge or its commands, a file type the app opens, the release pipeline or its workflows, a new dependency with a licence the allow-list does not name), re-read its row in `docs/architecture/threat-model.md`, update the row and bump its review date, and update `SECURITY.md` if the reporter-facing scope changed. If the change renames or moves a file, binding, event or bridge command that one of the Mermaid diagrams in `docs/architecture/` names (codebase map, first-use download, live teleprompter, REAPER bridge, in-app update), update the diagram in the same change; the diagram check (`pnpm check`) catches syntax, not a stale name. If the change adds a shipped dependency, the notices are regenerated by the release and the `allow-licenses` list in `.github/workflows/dependency-review.yml` may need an entry (see `docs/architecture/model-provenance.md` for models).
8. **Design drift.** If the change added types, interfaces, packages or dependencies, run `solid-design-review` pass 2 against the plan's Design check and fix or waive each finding before the final check.
9. **Final sanity check.** Run `git status` and review the diff of what's about to be committed — nothing unexpected, nothing suspicious, nothing left half-finished.

## What this skill is not

It doesn't replace `full-verification-gate` — cleanup edits still need that gate to pass. It also doesn't replace `code-reviewer`/`security-reviewer` for correctness or security review; this is specifically about not leaving a mess behind.
