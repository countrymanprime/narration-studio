# Design system reference

**Status: living document — describes current state, not a point-in-time decision.** Each entry links back to the ADR that justified it. Unlike `docs/adr/`, this file is meant to be edited as the system evolves; the ADRs underneath it are what stay immutable.

## Tokens

Design tokens are CSS custom properties defined in `src/studio/ui/src/styles.css`'s `:root` block, with dark-mode overrides in a single `:root[data-theme='dark']` block. New Tailwind-based components reference them via arbitrary-value syntax — `bg-[var(--surface)]`, `border-[var(--border)]`, `text-[var(--text-muted)]` — rather than duplicating values into `tailwind.config.js`. See .

Key tokens: `--bg`, `--surface`, `--surface-2`, `--surface-3`, `--border`, `--line-strong`, `--btn-line`, `--focus`, `--text`, `--text-muted`, `--non-text`, `--accent`, `--accent-strong`, `--accent-soft`, `--accent-contrast`, `--danger`, `--character`/`--place`/`--org`/`--review` (category colors), `--backdrop` (modal/drawer scrim; darker in dark, `rgba(0,0,0,.62)`, so a dark dialog stands off the page behind it, alignment audit R3EN2-15, R3MS-20), `--row-selected` (a selected row's tint, 8% accent in light and 16% in dark, where 8% all but vanished, XPF-28), `--danger-contrast` (the label on a filled danger button), `--shadow`, `--shadow-lg`. `--space-*`/`--font-size-*` are additive spacing/type-size steps (`--font-size-overlay-title`, 24 px, is the title of a `Dialog` and a `SlideOver`), grounded in values already repeated across the file — not a full scale, for new/touched code to converge on rather than picking another one-off rem value. `--z-*` is the one layer scale (`styles.css`, order pinned by `layers.test.ts`): `panel-scrim` 19 and `panel` 20 (a Script drawer, under the rail), `nav` 30, `takeover` 40, `slide-over-scrim` 45, `slide-over` 50, `popover` 55 (menus, context menus, anchored popups), `dialog` 60, `dialog-popover` 70, `toast` 80 (portalled to `<body>`, so a toast raised from a dialog or slide-over is drawn above it), `tooltip` 1000. A component names a layer with a token and never a bare number; a page panel is drawn inside its page (absolute), never fixed to the window, so it cannot cover the rail.

**Colour meets WCAG AA** ([Colour and contrast](colour-and-contrast.md); the rules, the token table, how to choose a colour and how the guard works are in [colour-and-contrast.md](colour-and-contrast.md)): there are two text levels, `--text` and `--text-muted`, and one colour for what is seen and not read, `--non-text` (icons, dots, glyphs). `--text-faint` no longer exists. Status text uses `--danger-text`, `--warn-text` and `--info-text` (`--danger`, `--warn` and `--info` stay for borders, dots and fills); the current navigation item is `--accent-strong`; highlights and entity badges draw `--<kind>-text` on a tint of the kind colour, and the eight kind colours have dark values. Placeholders are `--text-muted`. `src/studio/ui/src/paletteContrast.test.ts` holds every declared pair to 4.5:1 (text) or 3:1 (marks) in both themes.

Which colour and form a kind of thing gets follows what it is, not the page: [One colour and one form per kind](colour-and-contrast.md#one-colour-and-one-form-per-kind) holds the map and the accepted decisions CD1 to CD13 (2026-10-18), and the mock lines they supersede.

## Which mocks are the spec

The Studio Next mock (`docs/research/mockups/studio-next/`) is the frozen reference for every page it covers: its layout, tokens, primitive sizes and behaviour (owner ruling D98, 2026-10-11, amended 2026-10-18). It is not updated as the app changes; a departure supersedes the mock's line in the PRD or doc that covers the page. Where an older ADR, a benchmark mock or a value in this page differs, the mock wins until such a PRD or doc says otherwise. When a primitive, token or style does not draw what the mock shows, the primitive changes and every page inherits it; a page does not restyle it locally. The full rule, including what is not built and what stays as built, is in the Studio Next rebuild PRD's "Which mocks are the spec" section.

## Theme

The theme is one app-wide setting, light or dark (owner ruling D69). No page or surface forces light or dark, and a dark mock shows the dark theme, not a per-page look; the booth no longer forces dark ([Derived and status tokens](colour-and-contrast.md#derived-and-status-tokens)). `data-theme` on `<html>` is set by `ThemeProvider`/`useTheme` (`src/studio/ui/src/theme/`), a tri-state Light/Dark/System preference persisted to `localStorage`, exposed via a new "Appearance" category in `Settings.tsx`. An inline bootstrap script in `index.html` sets the attribute before first paint to avoid a flash of the wrong theme. See Theme.

### Native controls stay in the primitives

A control drawn smaller than 24 px (a `HeaderChip` button, the `Tooltip` info icon, a `Checkbox` box, a `Switch` track, a `Button variant="link"`, a toast's action and close) takes presses in the 24 by 24 px square around it without looking any bigger: `HIT_AREA` (`primitives/hitArea.ts`) adds an invisible centred box at least that size (WCAG 2.2 target size; alignment audit cause G). A new small control uses it, and `hitArea.test.ts` lists the ones that do. `HIT_AREA_32` is the same box at 32 px, for a control beside 32 px ones in a bar (the header's chips). `HIT_AREA_PLACED` is the 24 px box for a control that is already `absolute`, which it leaves in place: the Proof waveform's **Window start** and **Window end** handles, drawn 12 px wide on the overview, take presses 24 px wide.

A page builds a control from a primitive and never writes the native element. `src/studio/ui/src/rawNatives.test.ts` counts the native `button`, `select`, `input`, `textarea` and `table` parts written in JSX outside `components/primitives/`, and fails on the pasted icon-button look (`size-8` with `rounded-md`). Use `IconButton` for an icon-only button, `Button` for a text button, `TextField`, `SearchField` or `Field` for a text control, `NumberInput` for a number, `Select` for a choice, and `Table` for tabular data. Two things let a native element stand:

- **A marker.** A comment `native-control-ok: <reason>` of at least 12 characters on the element's first line or the line above leaves it out of the count, whatever its tag. The reason says what the element does that no primitive can. A marker with no native element under it is stale and fails.
- **A ceiling.** A per-file count that may only go down: a count above it fails, and so does a ceiling above the real count, so the entry is lowered or deleted in the change that removes the element. `select`, `textarea` and the table parts have none left; `button` has the most, and `input` is kept for three hidden file pickers.

`ZERO_DIRS` lists the folders built to the Studio Next mock (the schedule, readiness and pipeline folders so far). A native element there needs a marker or a primitive, a ceiling there fails, and a listed folder that no longer exists fails. A page swap adds its new folder to `ZERO_DIRS` and deletes the old page's ceilings in the same PR. A ceiling is therefore not the only escape: a marker is the way out for a new element no primitive draws, and a ceiling only records old debt.

### Import rules

Three import facts are checked, not reviewed ([Verification and code-health tooling](../operations/verification-tooling.md), `pnpm --dir src/studio/ui architecture`): a file in `components/primitives/` (a story or a test too) imports nothing else under `components/`, so shared data such as the chapter status labels sits above the feature folders (`src/chapterStatus.ts`); only `src/api/` imports the generated `wailsjs/` bindings and the Wails runtime (`@wailsio/runtime`, [ADR 0001](../adr/0001-the-app-is-written-in-go.md)); and only a primitive imports Base UI. `Highlight` is the only file that writes a `<mark>`, with one reasoned exception, the Script reader's Find bar match (the proofing diff's `InlineDiffRow`, the subject of , was deleted with the chapter workspace); `src/highlightBoundary.test.ts` is the check.

### Base UI wrappers

Interactive behaviour (focus trap, Escape, focus return, id wiring, roving focus) comes from Base UI (`@base-ui/react`), and only the primitives import it. To build a widget:

- **One flat file per primitive** in `primitives/`, with a `<Name>.stories.tsx` and a `<Name>.test.tsx` next to it (a multi-part primitive, `Tabs`, `Table`, `Collapsible`, keeps its parts in one file). A primitive that is only the browser's own element with our tokens (`Select`, `Table`) uses no library part. Import per component (`@base-ui/react/dialog`), never the package root.
- **A closed API.** Keep the props call sites already use, add only explicit new ones, never spread Base UI props and never export a Base UI type. `className` and standard DOM attributes are fine. A part that renders a button is composed with our `Button` through `render`.
- **Style with Tailwind and tokens only:** `var(--token)` values and data-attribute variants on the parts (`data-open:`, `data-starting-style:`, `data-disabled:`, `data-invalid:`), mutually exclusive states, no new class in `styles.css`, none of the library's example CSS.
- **Focus rings.** A primitive draws no focus outline of its own: the global `:focus-visible { outline: 2px solid var(--focus); outline-offset: 2px }` rule in `components.css` applies (the Studio Next mock's rule). Where a clipped scroll area or a grid cell cannot show an outside outline, the primitive keeps an inset ring or a negative offset, still coloured `var(--focus)` (`Dialog`, `SlideOver`, `WorkDialog`, `StageGrid`, `Table`, `Timeline`); `primitives/focusRing.test.ts` fails a primitive that names `--accent` for focus.
- **Stacking.** `#root` and the Storybook decorator are `isolate`, so a popup portalled to `<body>` is outside the app's stacking context and always above it. The numeric order among popups is slide-over 50, dialog 60, selection menu 65, nav drawer 70, tooltip and popover 1000.
- **Prove behaviour in a story.** A keyboard behaviour (Escape, Tab trap, focus return) is a `play()` in the wrapper's story, checked in the Chromium atlas; `stories.test.tsx` runs the same story in jsdom, which needs no polyfill for Base UI. Stories find portalled popups on `document.body`, not inside the story canvas.
- **The boundary is a test.** `src/baseUiBoundary.test.ts` fails on any `@base-ui/*` import outside `primitives/`, so a page that needs a new behaviour gets a new primitive first.
- **Bundle budget.** The production JS bundle (`src/studio/ui/dist/assets/index-*.js`) was 571,969 bytes raw (158,239 gzip) before Base UI, 787,619 raw (231,679 gzip) with every wrapper of the foundation stack, and 794,295 raw (237,296 gzip) with the native-control, tab, toggle-group, tag-input and table primitives (CSS 44,244): +38.9% over the start. At the Studio UI Primitives close-out, after the work landed alongside it (the DAW port, provider ports, input commands and the ten studio primitives), it measured 1,363,668 raw (401,962 gzip, CSS 75,553): +138.4% over the start, past the budget below. The growth is spread across the feature code landed since the previous measurement, not concentrated in the ten flat leaf files those primitives added. The budget is **800,000 bytes raw**, a documented number and not a CI gate: a change that takes the bundle past it (a Base UI minor bump, a new family) says why in its pull request; the bundle already being over it is a standing note for the owner, not a reason to block a change that doesn't grow it further. Measure with `pnpm --dir src/studio/ui build` and look at `dist/assets`. It is a desktop app served from disk, so the cost is parse time, not download.
- **What is not wrapped.** The alias combobox in `GuideDetail.tsx` (domain matching and an active index; its input is a `TextField`), `Button`, `NavButton`, `Heading`, `Panel`, `Highlight` and `ErrorBoundary` are plain components with no library part; a page that needs a new widget gets a new primitive.

The custom-CSS system (`.btn`, `.panel-head`/`.panel-body`, `.progressbar`, etc.) that was deliberately left in place for not-yet-migrated consumers has since been fully migrated to Tailwind utilities. New UI work should reach for Tailwind utilities directly rather than adding to `styles.css`. The [Base UI wrappers](#base-ui-wrappers) section also lists the small set of deliberate exceptions still in `styles.css` (scrollbar-hiding rules, keyframe animations, and a handful of unstyled "marker" classes kept only because visual/unit tests select by CSS class; the generic `table.dtable` style was the fourth and is gone, replaced by `Table`).

## Conventions

- **A mark placed on a track by time** (Proof's waveform pins, the window's handles) is a 24 px press target centred on its time with the dot drawn inside it, so dots of different sizes share one centre line, and its position is `clamp(half, x%, 100% - half)` so a mark at the start or end stays inside the card's text edges (`WaveformWindow.tsx`, alignment audit XPF-15, R3PF-6).
- **Read-only quoted text is a filled box, not a field.** Proof's Inspector draws what the script says and what was heard as the Studio Next mock's `.quote`: `--surface-2` fill, no border, the card radius (`quoteClass` in `components/proof/inspector/quoteStyle.ts`; on a tinted banner, the card's `--surface`), with the mock's `.diff` marks, a word struck on `--danger-soft` and a word heard instead on `--ok-soft` without an underline (alignment audit R4TB-5). A bordered box on `--surface` is a text field.
- **A run's phase is a step list, not a toggle.** Where a card shows which step a run is on (Proof chapter's Compare: Setup, Running, Results), it draws an `<ol>` of numbered steps with `aria-current="step"` on the current one, filled with `--accent`, 28 px tall so the card header keeps its height; a `ToggleGroup` would offer a choice the narrator does not have (alignment audit XPC-14, R3PC-3).
- **Numeric table columns are right-aligned** (`align="right"` on the `TableHeader`, `numeric` on its `TableCell`s) — see `DiagnosticsTables.tsx` (Delivery's diagnostics) for a reference implementation.
- **A card's one action sits with what it needs.** When a button is off, the reason is the line beside it (`aria-describedby`) and an option that only changes what it does is off with it; a card whose option and precondition sit in its body keeps the button there too, at the foot, not alone in the header (Master & QC's `ReportExportPanel.tsx`, alignment audit R4TB-4, R4MS2-3). A description too long for the header's line (more than a short subtitle) is the body's first paragraph, so a header stays the height of its neighbours (`MasteringChain.tsx`, XMS-15, R4MS2-10).
- **A group of peer commands is a grid of equal buttons, not a wrapping row of content-sized ones.** Each button fills its cell (`w-full`), the gap is 8 px (`gap-2`) and the column count steps down with the container (three, two, one), so the rows share their edges whatever the labels say. Reference: the engine panel's REAPER tools (alignment audit ENX-9).
- **A card's status facts are label and value rows (`dl`), not one line joined with dots.** The labels sit muted in their own column, so a status, a time and a wait read as separate facts (the engine panel's Chapter sync, R3EN2-3). A problem in a card is an `InsetCard tone="warn"` with its icon, the sentence and its remedies as buttons in the box (the REAPER project card's wrong-project notice, R3EN2-4).
- **A tool dialog's outcome is one result block, at the place the narrator is looking.** The engine panel's dialogs show a run's result, success or failure, as `engine/ToolResult.tsx`: an inset box led by a tone badge (Done, Check, Failed) and the message at regular weight, never bold body text or loose red text. Only the counts that are not zero are named. A failure is shown once, beside the action that failed, and after a run that finished **Close** is the primary (alignment audit R3EN1-3, ENX-22, ENX-28).
- **A check list that pairs a result with a value lays out on one grid**, the result pill in a fixed column so a label starts at the same x after "Pass" and "✕ Fail", capped (`max-w-[48rem]` in Master & QC's `FileChecks.tsx`) so a value stays near its label on a wide window. This departs from the Studio Next mock's `.optrow`, a flex row that pushed the value and the limit to the card's far edge (alignment audit XMS-14). In a rule table, how a requirement was verified sits under the requirement rather than in a narrow column of its own (`FileRulesPanel.tsx`, XMS-7).
- **A page's side column stays in view and comes early in one column.** Master & QC's aside (the delivery package and Multi-platform export) is `xl:sticky xl:top-0` beside a left column many screens long; below `xl` the left column's box gives way (`max-xl:contents`) and `order` puts the aside straight after the files card, before the lower panels (alignment audit XMS-4, XMS-5).
- **Master & QC's delivery package departs from the Studio Next mock in three places** (alignment audit R4MS1-5, R4TB-3, R4MS2-4, R4MS1-13, R4MS2-9): a check not judged yet is a hollow circle (`○`) in a fixed 28 px badge column, where the mock draws a "…" pill that read as a list still loading; the mock's caption under Open Delivery ("0 failing and 14 not ready.") is gone, since the rows above already say both counts; and Open Delivery keeps its own width and is off while the card loads. A Multi-platform export result sits under its own platform's checkbox, not in a second list of the same names (R4MS2-8, R3MS-14).
- **A message several rows share is said once, not on every row.** The card says it once above the table ("12 rows marked Waiting: no file measured yet · not mastered.") and a row keeps only a message of its own; a run's progress, its outcome and a read that failed sit in the card of the work they belong to, under its controls, at the card's inset, with the one button they offer at the card's right edge. See Master & QC's `FilesTable.tsx` (`sharedWaiting` in `rows.ts`). This departs from the Studio Next mock's Master page, which repeats "<reason> · not mastered" on every waiting row (alignment audit R4MS1-6). The jump menu does the same with an off reason: a run of rows in one group that share it ("Import a manuscript to unlock this page.") draws it once, on the run's first row, and the others keep it as a screen-reader hint; a sub-line that only repeats a word of the row ("zoom" under "Set zoom to 110%") is not drawn (`JumpMenu.tsx`, alignment audit XSL-6).
- **A data table whose rows change state fixes its columns** with `Table columns` (the label column `'auto'`, every other column a width that holds its heading and its longest value on one line) and a `min-w-*` floor on the table, so a long cell wraps in its own column, the headings never move between states and, under the floor, the table scrolls in its box rather than breaking a name a letter a line. See `FilesTable.tsx`.
- **A table of rows with controls keeps one line of controls per row, on fixed columns.** Its widths come from `Table columns`; the row's own action (Confirm, or Change and Clear) is a button pair at the right, and anything else the row can do is in a **More actions** `Menu` after it; status is a `StatusBadge`, not coloured text. Below a container width the row stacks into two lines rather than scrolling sideways. Reference: the engine panel's Chapter links (`engine/ChapterLinksTable.tsx`, alignment audit ENX-1 to ENX-5, ENX-29).
- **A select whose choice links or writes something opens on its placeholder, never on its first option,** and the action it feeds stays off until a choice is made, so one press cannot act on a value nobody picked (`mapping/MappingConfirm.tsx`, `TrackSelect`'s "Choose a track", alignment audit R3EN2-1). Where a matcher has a best match, preselecting that one is allowed (`trackChoices`).

## Layout and scrolling

The document (`html`/`body`) never scrolls; it is locked (`overflow: hidden`, `styles.css`) once nothing needs it to. Every page scrolls inside the shell's own page area (`AppShell.tsx`'s `<main>`, `.scroll-chrome-hidden`), which is the shell's single scroll container and also gives absolutely positioned descendants (an `sr-only` label, a Base UI hidden input) a containing block so they scroll and clip with their row instead of escaping to the window. The shell is sized off a `height: 100%` chain from `html`/`body`/`#root` (`h-full`), not `100vh`/`100dvh`, because only the `%` chain stays exact under both WebView2's zoom and a CSS `zoom` on `<html>`.

## Page width

One policy, proposed in #2654 and applied by `PAGE_COLUMN_CLASS` (`primitives/pageColumn.ts`, `pageWidthPolicy.guard.test.ts`):

- **A data page is one column of up to 96 rem (1,536 px), centred.** Master & QC, Delivery and Pickups use it. Below 96 rem the page fills the window, so nothing changes at 1280 or 390 px. Above it, a table's text column no longer stretches with its status and actions at the far edge (Pickups at 1920 px was a 1,270 px table with a 700 px line column, now at most the 96 rem column less the 380 px session panel).
- **A workspace page fills the window.** Script, Booth, Editing and Proof are panes around a reading column or a waveform. Their text is `ReaderColumn`, never a page cap.
- A new page picks one of the two. It does not write its own `max-w-*` or `mx-auto` for the page.

Not changed by this policy: Production, Story Bible and Schedule keep their current widths until a screenshot at 1920 px shows a gap like Pickups'.

## Layout rules

Four widths and the rail decide the layout, as the Studio Next mock lays it out:

| Class | Applies | Meaning |
| --- | --- | --- |
| `railCollapsed` | below 1360 px | The rail shows icons only. The editing timeline strip sits under the script from 1360 px (`STRIP_MIN_WIDTH`) and is part of the drawer below it |
| `medium` | 1280 px and below | Busy side columns become drawers or stack. This is the one inclusive bound |
| `narrow` | below 1180 px | Narrow layouts |
| `tiny` | below 860 px | Tiny layouts |

**Where they live.** `src/studio/ui/src/layoutBreakpoints.ts` holds the numbers, `layoutClassFor(width)` and `LAYOUT_QUERIES`, one media query per class. `useLayoutClass()` (`src/hooks/useLayoutClass.ts`) follows those queries for the places CSS cannot decide, and returns the full layout where there is no `matchMedia` (jsdom). Tailwind cannot read a constant inside a class name, so a page writes the width variants out: `min-[1360px]`, `max-[1360px]`, `max-[1281px]`, `min-[1281px]`, `max-[1180px]`, `min-[1180px]`, `max-[860px]` and `min-[860px]`. Tailwind 4's `max-[N]` is `width < N`, so each `max` carries the same number as its `min` (`max-[1281px]` is 1280 px and below). `src/layoutQueries.test.ts` scans the source, fails a variant between 860 and 1440 px outside that list unless the file's count is recorded in `OFF_VOCABULARY` (counts only fall), and fails a width compared with one of the four numbers outside the hook. The scan, not an import, links the classes to the module.

**Zoom.** The rules read the reported CSS width, not a zoomed one, so host zoom moves a window across a band: a 1440 px window at 200% reports 720 px ([Zoom](../guides/using-the-app/navigation.md#zoom)). The mock's `style.zoom` mechanism is not used.

**What the visual suite draws.** The matrix is 1440, 1024 and 768 px. Two bands it would miss are drawn by rows that opt in with `LAYOUT_BANDS`: 1300 px (rail collapsed, not yet medium) and 1230 px (medium, not narrow). The 390 px reflow width is for rows that opt in with `extraViewports`. There is no phone viewport ([viewports.ts](../../src/studio/ui/tests/visual/viewports.ts)).

**A bar that wraps keeps its tools together.** A page's top bar that wraps (`flex-wrap`) puts its trailing chips and icon buttons in one `ml-auto` group that does not wrap inside, so a narrow window moves the whole group to the next row at the right edge instead of leaving one tool under the first button of the bar (the Booth's `BoothTop`, `[data-booth-tools]`; alignment audit XBO-3, R3BO-2). A spacer `flex-1` does not do this: it only pushes on the row it lands on. The bar's chips are one family, the 22 px pill (`HeaderChip`, or `Badge` `shape="pill"` for one that is not a button, such as the Booth's REC and Pickups chips), never the 26 px `booth` tag beside a pill (XBO-11). In the medium layout the Booth's chapter picker is as wide as its name up to the wide layout's 340 px, not the mock's fixed 190 px (`.md .booth .chapbar .chapsel`), which cut short names while the bar had room (XBO-22); the bar wraps instead. Two more departures from the mock's Booth bar: its progress line says "~8:10 of audio left" where the mock says "finished left", which read as a typo (R4BO2-11), and its Resume chip is not drawn while the reading position is already in the offered paragraph (R4BO1-3, R4BO2-10).

## No in-flow instructions

Help text lives in a tooltip, a "?" overlay or the page's guide. Nothing instructional may take room in a page or change a container's size when it shows, hides, wraps or is translated (owner, 2026-10-26, #2251, after a two-line gesture manual under the Editing waveform).

- **In flow, only what the narrator is looking at.** A page draws data (a range's time, a count), the state of the thing in front of the narrator, an error with what to do about it, and an empty state in one line. It never draws how to use a control, a gesture list, a "Tip:" line or technical background ("the host keeps 50 peaks a second").
- **Data that comes and goes has a reserved slot.** Text that appears with a selection or a reading sits in a fixed-height slot, so showing or hiding it moves nothing (the Editing waveform's notes line).
- **A hint is a few words on one line.** A `Tooltip`, `TooltipTarget`, `title`, `hint`, `disabledReason` or `reason` is at most 80 characters and one sentence, has keyboard access (the primitives give it), and never holds the only copy of something the narrator needs to act. Gestures for a surface go on its "?" (`Tooltip` with `icon="?"`, as the waveform's "Waveform gestures"). A few sentences go in a `HelpButton`, a "?" that a press opens as a popover; anything longer goes to the guide.
- **Settings.** A row's description (`desc`) is one short line (60 characters); its details (`more`) open from a **?** beside its name (`HelpButton`, a popover a press opens). A category blurb is one line (80 characters).
- **Dialogs and slide-overs** may explain what their action does, since they cover the page instead of moving it. Keep it to what the narrator needs to decide.

**The guard.** `src/studio/ui/tests/visual/inFlowProse.test.ts` reads every non-test `.tsx` with the TypeScript parser (`tests/visual/prose/extract.ts`) and finds every run of prose: JSX text over 60 characters or two sentences, and text-bearing props. Each must be listed in `tests/visual/prose/prose-inventory.ts` with its class (`overlay`, `error`, `empty`, `state`, `instruction`, `explanation`), an entry whose text is gone fails, and the `instruction` and `explanation` entries are capped by `MAX_IN_FLOW_INSTRUCTIONS`, which may only go down. It also fails a hint over the length rule, a category blurb over one line, and any Settings description over 60 characters (`MAX_LONG_SETTING_DESCRIPTIONS` is 0). It reads source, not the rendered page: text built in a variable and passed to JSX (`{note}`) is not seen. The inventory, page by page, is in [the in-flow prose inventory](../research/in-flow-prose-inventory.md).

## Errors

An error shows as a `Toast`, in a modal, or in a result box that is always on the page at a fixed size. It never appears as text in the page's flow, because that moves the layout when it shows (owner, 2026-10-27). `src/studio/ui/tests/visual/guards/inlineErrors.test.ts` counts `role="alert"` elements outside dialogs, menus, popovers and the toast, per file, against `inline-errors-allowlist.ts`; the list may only shrink. `tests/visual/guards/toolbarButtons.test.ts` does the same for a `Button` with words inside a toolbar or ribbon (`toolbar-text-buttons-allowlist.ts`): a toolbar holds icon buttons with a tooltip and an `aria-label`. The rest of the checklist is the `frontend-primitives` skill.

## Settings rows

The Settings page always keeps every setting. A working page may also offer a compact entry for one (a menu, a modal or a drawer tab, hidden until opened) that edits the same keys, but it never replaces the Settings control; `registry/pageSettings.test.ts` fails when a page-owned setting has no Settings panel.

`src/studio/ui/src/components/settings/ScopedSetting.tsx` renders one Settings field by its `kind`, and the host (`src/studio/desktop/app.go`, `fieldSchemas` and `validateSettingValue`) validates it by the same kind. Every value is a string in the settings files.

| Kind | Control | Stored value |
| --- | --- | --- |
| `choice` | `Select`, full width of its column | one of the schema's choices |
| `text` | `TextField` | any string |
| `color` | a colour swatch and a mono hex `TextField` on one line | six hex digits, no `#`, capitals |
| `bool` | `Switch`: the row is the switch (named by the setting), its hint icon and Reset, not a label column and a control column | `"true"` or `"false"`; anything else reads as off and the host rejects it |

**Layout.** The Settings page draws each setting with `src/studio/ui/src/components/settings/row/SettingRowView.tsx` (`ScopedSetting.tsx` draws the fields of a settings tool's panel). Its row is the same two columns, measured on the page's own width (`SETTING_ROW_GRID`): stacked below 761 px, a 12rem label column from 761 px and `minmax(12rem,16rem)` from 860 px (one of the layout widths in `layoutBreakpoints.ts`); a select and a text box are one width, 20rem (a program path 26rem), so the controls down a category line up (alignment audit cause E); that width is a cap on the column's width (`w-full` with `max-w-80`, the control's row `w-full`), so in a narrow column a box ends at the card's padding instead of running past the card and the window (XSE2-1, `tests/visual/settings-fields.spec.ts`). In `ScopedSetting.tsx`, below `md` (768 px) the label stacks above the control; from `md` to `lg` the label column is a fixed 12rem, from `lg` `minmax(12rem,16rem)`. A grid gives a fixed-range track its full maximum before a flexible one gets any, so a two-column template with no breakpoint left a 45 px control at a 390 px window (defect 8, [Visual bug fixes require screenshot verification](../../.claude/rules/ui-visual-verification.md)). Selects and text boxes take the free width (`flex-[1_1_10rem]`, `min-w-0`) up to `max-w-md`, so every select is the same width; the hex box has a 4.5rem minimum beside its swatch; the control row wraps, so Reset shares the line and drops under the control only when there is no room (it does at 768 px). ## CSS layering gotcha

`styles.css` wraps only *some* rules in `@layer base`/`@layer components` (roughly lines 66–616); everything after that is unlayered plain CSS. Unlayered rules always beat Tailwind utilities (which live in the implicit `@layer utilities`) for the same property, regardless of source order. Before adding a Tailwind override next to a legacy class name, check whether that class is inside a `@layer` block — if it's unlayered, the Tailwind utility will silently do nothing for any property the legacy rule already sets.

**Same property, two widths.** Tailwind emits the named-scale media blocks (`xl:`) as a later group than the arbitrary ones (`min-[1281px]:`) whatever their pixel value, so a named variant overrides a narrower arbitrary one at wide widths. Two variants that set the same property at different widths must both be arbitrary or both be named; pages write widths as arbitrary `min-[Npx]` variants for this reason.

## What the suites do not prove

The visual suite is a gate on errors and on measurable alignment, not on appearance: it fails on page errors, failed requests, sideways overflow, a collapsed control (a text box or select under 64 px, [Visual bug fixes require screenshot verification](../../.claude/rules/ui-visual-verification.md); the Settings rows are also captured at a 390 px reflow width), two sibling controls on one row whose heights differ by more than 1.5 px (a select beside a button; `findMixedRowHeights`, alignment audit rule A6), a hit of an alignment rule (the [alignment audit's](../research/alignment-audit.md#alignment-rules) DOM rules, measured on every capture by `src/studio/ui/tests/visual/lib/layoutScan.ts`: like rows that do not share their edges, columns, last actions or heights, controls off one centre line or stacked beside their row, a margin label (a paragraph's time) off the centre of the first line beside it, a wrapped or needlessly truncated label, text cut at a box's edge, overlapping text, cards side by side of unequal height, a flush table inset from its card's title, uneven gaps between like items, a selection bar narrower than its block, a card off the page gutter, a click area that stops short of its card or a hit area under 24 px beside another target (W5, content under a scrollbar, is not measured: the headless browser draws no scrollbars); a known hit is declared in `src/studio/ui/tests/visual/layout-debt.ts` with the defect as measured, and an entry that stops being found fails too, so that list only shrinks), blank screenshots and two states that render identically without a declared `sameAs`; beyond the alignment rules it says nothing about whether a layout looks right. Axe runs on Storybook stories in the atlas (`src/studio/ui/tests/atlas/atlas.spec.ts`) and on every app state in the visual suite: a violation fails the capture unless `src/studio/ui/tests/visual/axe-debt.ts` declares it with a reason, and a declared rule that stops being reported fails too, so the list only shrinks ([CI and releases](../operations/ci-and-releases.md); `UI_AXE=1` measures without failing). Aria snapshots pin the role trees of the dialogs, the slide-over and the navigation in a run of their own (`src/studio/ui/tests/aria`, [Verification and code-health tooling](../operations/verification-tooling.md)). None of this can judge gradients or low-contrast text over semi-transparent overlays, focus order or what a screen reader announces, so contrast by eye and a screen-reader pass remain. Pixel baselines are not adopted: the captures on one machine are now byte-identical from run to run (282 of 282 PNGs across repeated and CPU-throttled runs on the same Windows machine), which does not reproduce the earlier measurement (9 of 244 differing between two runs); but all of those runs were on one machine, nothing here shows that two machines or operating systems agree, and a baseline would have to come from a pinned Linux container. The spike that would decide this is [#153](https://github.com/countrymanprime/narration-studio/issues/153), after the suite has been stable for 50 runs, and its result is recorded as an ADR either way. The suite's own reliability rules (waits are conditions, `UI_CPU_THROTTLE` to prove a driver) are in [CI and releases](../operations/ci-and-releases.md#keeping-a-red-run-meaningful).
