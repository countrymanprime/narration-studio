# 0780. The jump menu, context menus and help are derived from the static command catalogue, and dynamic commands come from providers

**Status:** Accepted (owner ruling 2026-10-11; owner rulings SNR-Q1 and SNR-Q3 of 2026-10-11, register row A3; both were taken as defaults under the standing instruction)
**Date:** 2026-10-11
**Supersedes:** none. It extends [ADR 0361](0361-app-commands-go-through-one-registry-and-keyboard-midi-and-hid-are-input-sources-bound-by-a-remappable-keymap.md) and keeps all seven of its decisions.

## Context

In the Studio Next mock a page adds a command, a key, a right-click menu, a search source or a help row by registering it in one place, and the jump menu (Ctrl+K), the shortcut sheet and the context menus follow. The registrations are in `docs/research/mockups/studio-next/src/app/registry.ts` (`registerContext`, `registerCommands`, `registerSearch`, `registerKeys`) and are made at import time. `registerCommands(() => Command[])` returns commands that are rebuilt on every read, so a command can depend on live data (go to chapter 3). `registerKeys(page, fn)` hands a page a raw `KeyboardEvent` handler.

The real app has a static catalogue of 15 commands (`apps/ui/src/input/commands.catalog.ts`), `ShortcutSheet` with its own list, `ContextMenu` with its items written at each call site, and no jump menu or search. Porting the mock's registries as they stand would break two rules that bind:

- [ADR 0361](0361-app-commands-go-through-one-registry-and-keyboard-midi-and-hid-are-input-sources-bound-by-a-remappable-keymap.md) decision 1 makes commands static descriptors, with a test that fails when an id is missing from the catalogue or a row is never registered. Decision 2 says features never listen to `keydown` for a command, and a scan test fails on a listener outside `src/input/`. `registerKeys` is exactly such a listener.
- A keymap the narrator can remap (decisions 4 and 5) only works if every shortcut is a catalogue row. A key a page registers on the side cannot be remapped, listed or checked for conflicts.

What the mock does not have to solve is data that is not known at build time: the chapters of the open book, bookmarks, Story Bible entries. Those need a way into the jump menu that is not a catalogue row.

## Decision

1. **The catalogue stays the one list of commands with keys.** `CommandDescriptor` gains optional `group` (the jump menu heading), `hint` and `surfaces` (`jumpMenu`, `help`, `settings`). Keys stay in the keymap and handlers stay `useCommand(id, handler, enabled)` ([ADR 0361](0361-app-commands-go-through-one-registry-and-keyboard-midi-and-hid-are-input-sources-bound-by-a-remappable-keymap.md) decision 1). A static row is always in the surfaces it names.
2. **The mock's `registerKeys` is not adopted.** A page that needs a key adds a catalogue row and a `useCommand` call. [ADR 0361](0361-app-commands-go-through-one-registry-and-keyboard-midi-and-hid-are-input-sources-bound-by-a-remappable-keymap.md) decision 2 and its scan test stand without a new allowlist entry. The mock's `registerCommands(() => Command[])` is not adopted either: a function that returns commands, with a key attached to each, would put commands outside the catalogue.
3. **Dynamic commands come from providers, and a provider's commands never carry a key.** `CommandProvider = () => ProvidedCommand[]`, `ProvidedCommand = { id, group, label, hint?, run }`. A provider's results appear in the jump menu only. They have no default gesture, are not in the keymap, and do not appear in the shortcut sheet or the Settings key list. A command that needs a key is a catalogue row, and its target is chosen after it runs (a catalogue `nav.chapter.next`, not a key per chapter).
4. **Chapters come from providers (SNR-Q3).** "Go to chapter 3" is a provided command, not a catalogue row. The catalogue test that checks every id and every surface covers static rows only; a provider has its own unit test.
5. **Search sources register by function.** `SearchSource = (term: string) => SearchHit[]`, `SearchHit = { group, title, sub?, run }`, for manuscript text, Story Bible entries, marks and bookmarks, with the heading and sub-line the mock draws (`studio-next/src/app/search-sources.tsx`). Which sources exist at which phase is the PRD's, not this ADR's.
6. **The jump menu is a derived view.** It lists static catalogue rows whose `surfaces` include `jumpMenu`, then provider commands, filtered by the typed term. With a typed term, search hits come before the commands, as `studio-next/src/app/palette.tsx` and `apps/ui/src/components/layout/JumpMenu.tsx` do. It opens on `jump.open` (Ctrl+K). Ctrl+F is Find in Script and opens the jump menu on every other page, as `studio-next/src/app/keys.ts` does (SNR-Q1); the catalogue gains `find.open` for the Script half. The jump menu does not replace navigation: the rail stays, and a collapsed rail opens over the page on hover (SNR-Q2).
7. **Context menus resolve through providers and one host.** `ContextProvider = { match(target: Element): boolean; items(target: Element): ContextMenuItem[] }`. One `ContextMenuHost` mounted over `<main>` resolves the target under the pointer, or the focused element (or its `aria-activedescendant`) for the Menu key and Shift+F10, and renders the existing `ContextMenu` popup ([ADR 0705](0705-the-workspace-adds-an-effect-to-a-passage-or-a-chain-to-the-chapters-track-only-after-the-narrator-confirms-and-the-host-names-both-targets.md) is extended, not replaced). Menu and Shift+F10 are catalogue rows; the host does not add a `keydown` listener. There is no `contextmenu` listener on `document`, and text fields keep the browser's menu.
8. **Help is the keymap.** `ShortcutSheet`, the Settings key list and the key-hint footers read one table derived from the catalogue, the narrator's remapped gestures from the keymap, and per-surface hint specs (which keys a footer shows, in what order). The sheet shows the keys the narrator has set, not the defaults.
9. **A leave guard is the one other registration.** `LeaveGuard = (next: Location) => 'allow' | { ask: ConfirmSpec }` lets a page ask before a page change. It is not a command and carries no key.
10. **Import direction.** Registries live in `apps/ui/src/registries/` and are imported by features; a registry imports nothing from a feature ([ADR 0062](0062-ui-import-rules-are-a-dependency-cruiser-config-and-a-mark-scan-that-name-their-adr.md) rules, enforced by dependency-cruiser). `JumpMenu` and `ContextMenuHost` live under `components/layout/` and are built from `Dialog`, `Listbox` and `ContextMenu`, so no new Base UI import appears outside the primitives ([ADR 0047](0047-the-ui-primitives-wrap-base-ui-and-app-code-never-imports-it.md)).
11. **The jump menu acknowledges within 100 ms** ([ADR 0075](0075-every-action-that-leaves-the-interface-acknowledges-within-100-ms-cannot-be-fired-twice-and-tells-the-narrator-when-it-ends.md)): it opens, and a typed term filters, without waiting for the host.

## Consequences

- A page worker adds rows and providers and never edits the shell, the jump menu or the help sheet. The PRD's test of that is a page slice that edits one of them after the shell phase.
- Every shortcut is still listed, remappable and conflict-checked, because no key exists outside the catalogue. A provider's command is reachable by typing only, which is the cost of keeping it out of the keymap: a narrator cannot bind "go to chapter 3" to a pedal. A pedal that steps chapters binds to the catalogue's step commands.
- The catalogue test cannot prove that every chapter, bookmark or entry is in the jump menu. Provider and source unit tests carry that.
- The mock's page key handlers (`registerKeys`) have no port. A mock behaviour that needs a key not in the catalogue becomes a catalogue row in the slice that builds the page.
- To allow a feature to listen for a key itself, to give provided commands default gestures, or to make the catalogue dynamic, write a new ADR that supersedes this one and [ADR 0361](0361-app-commands-go-through-one-registry-and-keyboard-midi-and-hid-are-input-sources-bound-by-a-remappable-keymap.md) decisions 1 and 2.
