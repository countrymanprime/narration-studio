# 0761. Layout rules read the reported width, the icon vocabulary is a data module, and key caps are pictures in a new KeyCap leaf

**Status:** Accepted (owner ruling 2026-10-11; owner rulings SN0-Q7, SNF-Q1 and SNF-Q2 of 2026-10-11, register row A16; SNF-Q1 and SNF-Q2 were taken as defaults under the standing instruction)
**Date:** 2026-10-11
**Supersedes:** none. It extends [ADR 0620](0620-kbd-draws-plex-mono-caps-in-two-sizes-with-a-pressed-bottom-edge-and-keyhint-composes-one-with-its-action.md) and keeps [ADR 0037](0037-visual-suite-captures-no-phone-viewport.md), [ADR 0061](0061-settings-states-are-also-captured-at-a-390px-reflow-width.md) and [ADR 0201](0201-app-zoom-under-wails-v3-on-windows-runs-from-100-to-200-percent-and-reads-the-level-back-from-the-window.md)

## Context

The Studio Next mock draws every page from one icon map, one key-cap mapping and responsive rules keyed to the zoomed viewport width (see [A1](0760-the-studio-next-mock-is-the-only-spec-for-every-page-it-covers-tokens-primitive-sizes-and-layouts-included.md) for why the mock is the spec). Three things in the repo stand between it and the mock:

- **Layout.** `docs/research/mockups/studio-next/src/app/layout.ts` sets `RAIL_COLLAPSE_BELOW = 1360`, `medium` at 1280 and below, `narrow` below 1180, `tiny` below 860, and a timeline strip that fits from 1360 (`STRIP_MIN_WIDTH`). It reads `document.documentElement.clientWidth` after setting `style.zoom`. The real app zooms through the host and reads the level back ([ADR 0201](0201-app-zoom-under-wails-v3-on-windows-runs-from-100-to-200-percent-and-reads-the-level-back-from-the-window.md)); the desktop window's minimum is 960 CSS px; the visual suite captures 1440, 1024 and 768, and 390 for the Settings states ([ADR 0037](0037-visual-suite-captures-no-phone-viewport.md), [ADR 0061](0061-settings-states-are-also-captured-at-a-390px-reflow-width.md)). The earlier recommendation for the rail was to collapse at 1280; the owner ruled 1360 (SN0-Q7).
- **Icons.** The mock draws every icon through `docs/research/mockups/studio-next/src/ui/Icon.tsx` and a vocabulary decided in `docs/research/mockups/studio-next/research/icon-audit.md` (sections 5 and 6: keep, change or text per action). 55 files in `apps/ui/src` import `FontAwesomeIcon` directly, so two pages can give one action two icons; the audit found such cases (sections 3a and 3b).
- **Key caps.** `docs/research/mockups/studio-next/src/ui/KeyCap.tsx` maps key names to pictures: arrows, Enter, Esc, Tab and Backspace as Font Awesome glyphs, the space bar and right-click as inline drawings. The repo's `Kbd` and `KeyHint` draw text caps only ([ADR 0620](0620-kbd-draws-plex-mono-caps-in-two-sizes-with-a-pressed-bottom-edge-and-keyhint-composes-one-with-its-action.md)).

These are one record because the register groups them as row A16 and the foundations PRD builds them in one series, but they are three separable rules; a later change to one supersedes only this ADR's matching item.

## Decision

1. **Layout rules are container or media queries at the mock's widths, read from the width the host reports.** The rail collapses to icons below 1360 CSS px; the medium layout applies at 1280 and below; narrow below 1180; tiny below 860; the editing timeline strip sits under the script from 1360 and is part of the drawer below it. The widths are the mock's values in `layout.ts`. The rules read the reported CSS width, so host zoom ([ADR 0201](0201-app-zoom-under-wails-v3-on-windows-runs-from-100-to-200-percent-and-reads-the-level-back-from-the-window.md)) moves a window across a threshold as it does in the mock, and the 960 px minimum window does not change them. The mock's `style.zoom` is not adopted. A hook, `useLayoutClass`, returning `{ rail: 'full' | 'icons', medium, narrow }` exists only where CSS cannot express a rule. The visual suite's widths stay as [ADR 0037](0037-visual-suite-captures-no-phone-viewport.md) and [ADR 0061](0061-settings-states-are-also-captured-at-a-390px-reflow-width.md) set them; a rule none of them exercises gets its own visual row (1440 is above every threshold, 1024 is below 1180, 768 is below 860, and no default width lies between 1180 and 1360, so the icon-only rail with a medium-or-wider layout is the case that needs one).
2. **The icon vocabulary is a data module, `apps/ui/src/icons.catalog.ts`.** It maps an action name to an icon and its tooltip wording, following `icon-audit.md` sections 5 and 6: text only for primary calls to action, segmented controls, chips and the audit's explicit text conversions; everything else an icon button with a tooltip; a navigation or rail icon is never reused as an action; near-identical icons are not placed side by side. A new `Icon` wrapper and `IconButton` read the catalogue, and a test checks that every action has a tooltip and that no two entries share an icon with different meanings. The mock's own icon map is not ported as a second icon system, and a ratchet test counts direct `FontAwesomeIcon` imports per file and lets the number only fall.
3. **Key caps are pictures chosen by a new `KeyCap` leaf, and `Kbd` stays text.** `KeyCap` resolves a key name against a glyph map (`KEY_GLYPHS` in the mock) and draws a glyph for arrows, Enter, Esc, Tab, Backspace, Space and right-click and the key's text for every other key; a glyph key carries its name as the accessible name and as a tooltip. `KeyChord` draws several, `KeyHint` composes a `KeyCap` with its action, and a `KeyHints` footer primitive replaces the hand-built rows in the Booth, Proof and Editing footers. [ADR 0620](0620-kbd-draws-plex-mono-caps-in-two-sizes-with-a-pressed-bottom-edge-and-keyhint-composes-one-with-its-action.md) is extended, not replaced: `Kbd` still only draws text caps, in Plex Mono at its two sizes with the pressed edge.

## Consequences

- Page slices need no layout, icon or key-cap work of their own: they read the catalogue, use `KeyHint` and `KeyHints`, and write container or media queries with the four widths.
- The rail collapse moves from the earlier 1280 recommendation to 1360, so a 1280 px window shows the icon-only rail, which the mock does.
- Because the rules read the reported width and not a zoomed width, a narrator at 200% zoom on a 1440 px window crosses the thresholds the same way the mock does, with no second mechanism to keep in step.
- Adding an icon means adding a catalogue row; page slices that add icons append to one file, which can conflict mechanically. Direct `FontAwesomeIcon` imports are not removed in bulk: each page's swap migrates its own files and the ratchet only falls.
- Three rules in one ADR means a change to the key-cap pictures also edits the record of the layout rules. They were kept together because the register and the PRD treat them as one base; split them in a later ADR if they start to change on different schedules.
- The glyph map draws its pictures from Font Awesome Free (already a dependency) and two inline drawings; adding a key means adding a map entry and a story.
- To change any of the three rules, write a new ADR that supersedes this one.
