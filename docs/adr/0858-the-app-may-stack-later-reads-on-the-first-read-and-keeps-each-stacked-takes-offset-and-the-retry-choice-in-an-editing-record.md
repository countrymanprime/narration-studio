# 0858. The app may stack later reads on the first read, and keeps each stacked take's offset and the retry choice in an Editing record

**Status:** Proposed
**Significance:** A persistence strategy and an interface between parts: a new file the host reads back (`editing/stacks.json`), five bindings the Editing page and the DAW stacking slices build to, and the app-side half of DQ-7. Reversing it removes un-stacking after a restart and changes the bindings, the schemas and the port.
**Date:** 2026-10-12
**Supersedes:** in part, [ADR 0147](0147-retakes-on-fixed-lanes-are-chosen-by-lane-play-state-and-the-app-never-converts-takes-and-lanes.md), to the extent of DQ-7: the app may offer to stack later reads onto the first read as takes, which 0147's "the app never converts takes and lanes" ruled out; its lane rules stand. [ADR 0860](0860-a-roll-keeps-the-earlier-audio-as-a-take-and-a-range-cut-a-chain-on-a-range-and-stacking-move-audio-and-never-delete-it.md) point 4 is the DAW half (the `stack_takes` and `unstack_takes` commands); this ADR is the app's record of what they did.

## Context

The Studio Next mock lets the narrator stack the retries of a passage: the later reads move onto the first read's spot as takes, and the audio after them moves up (`docs/research/mockups/studio-next/src/state/commands/stacking.ts`, `stackRetries`, `unstackRetries`). Un-stacking puts each take back "by the recorded offsets": the mock's `PassageStack` (`src/domain/schemas.ts`) keeps, by take id, the seconds after the first read's start where each stacked take began before it was stacked, and a take leaves that list when it is un-stacked. The narrator also chooses how retries are kept, `RetryMode` `stack` or `leave`, for the project (`editor.retryMode`, default `leave`), a chapter (`editor.retryChapters`) or a passage (`Passage.retryMode`). The mock's tests ask that the stack and the mode are valid against the schema with stable ids, that un-stacking reads the recorded offsets back, and that a Booth recording that merges passages again keeps both (`tests/d3-stacking.test.tsx`).

The [Script-Based Editing PRD](../prds/studio-next-script-based-editing.prd.md) asks for stacking as the mock does it (item 7) and decides that ADR 0147 is superseded to that extent (DQ-7). ADR 0860 point 4 built the REAPER commands; REAPER keeps where each moved item was in the take's `P_EXT`, but the page needs the offsets to show the un-stack plan and to name the takes, a DAW with no take extension data (Audacity, the built-in recorder) keeps nothing, and a page's state does not survive a restart. Nothing on the host kept the offsets or the mode ([#1290](https://github.com/countrymanprime/narration-utils/issues/1290)).

**Considered options:** keep the offsets only in REAPER's `P_EXT` (Audacity and the built-in recorder have none, and the page could not show the plan without a DAW call); keep them on the passage list (re-reading passages from a newer Booth map would drop them, which the mock's merge test forbids); put the retry mode in the settings file (the project, chapter and passage levels name chapter and passage ids, which go stale when the manuscript is replaced, as the other Editing records do); and the chosen one: one more Editing record, beside the others, holding both.

## Decision

1. **The app may stack.** The Editing page may offer to stack a passage's later reads onto its first read, and does so only after the narrator confirms and the DAW accepted `stackTakes` (ADR 0860 point 4). The first read never moves. Nothing is deleted: a stacked read's own item sits on the muted Cuts track, and un-stacking puts it back.
2. **One file, apart from the passage list.** `<project>/narration-utils/editing/stacks.json` (`editlog.StacksFile`, `apps/desktop/internal/editlog/stacks.go`), version 1: `{"schemaVersion": 1, "stacks": [...], "retry": {"project", "chapters", "passages"}}`. It is narrator data read through `persist` as [ADR 0856](0856-the-editing-records-are-one-file-per-kind-keyed-by-word-with-its-text-checked-on-read-and-cleared-when-the-manuscript-is-replaced.md) point 2 says: a file that breaks a rule is kept aside, a newer version is refused and never overwritten, a write goes through a temporary file and a rename. Re-reading passages, including a new Booth run, never touches it.
3. **A stack is offsets by take id.** One stack per passage, `stk-<passageId>`: its chapter, its first read (`base`), and `offsets`, the seconds after the first read's start where each stacked take began, by the take's id. Passages and takes are named by the ids the Takes panel offers; an id with a space, a control character, a slash, a backslash or an angle bracket, or over 256 characters, is refused, and nothing in the file is ever opened, run or fetched. An offset is finite, 0 or more and at most 7 days.
4. **A record needs the DAW's accepted result.** `EditingStackRecord(chapterId, stack)` takes the passage, its first read, the takes it offers, the moves, and the result: the mode (`native`, `app` or `steps`), the undo steps, and for `steps` the steps and the backup taken before them. It refuses, with a sentence and nothing saved, a first read or a moved take the passage does not offer, the first read moved onto itself, a take moved twice, an offset out of range, no move, a take already stacked on the passage, a passage already stacked on another first read, a chapter the manuscript lacks, and a missing or inconsistent result. A record on a stacked passage adds takes to it and keeps the latest result.
5. **Un-stacking removes offsets.** `EditingStackRemove(chapterId, passageId, takeIds)` forgets the named takes once the DAW put them back, or when the journal undoes the stack; some takes for a partial un-stack, and the stack goes with its last take. A take not stacked is not an error.
6. **The retry mode has three levels.** `EditingRetryModeSet(level, chapterId, passageId, mode)` sets `stack` or `leave` for the project, a chapter or a passage, and an empty mode takes it back. `EditingRetryModeGet` resolves the passage's own, else its chapter's, else the project's, else `leave`, and says which level it came from. The mode decides only what the page offers: nothing is stacked by itself.
7. **Recording changes nothing in the DAW, and replacing the manuscript clears the file.** The record is the app's memory of what the DAW did. Replacing the manuscript and Clear project data remove `stacks.json` (`resetDerived`); the DAW's audio stays as editing left it.
8. **The wire.** `PassageStack`, `RetryMode`, `EditStacksApi` (`apps/ui/src/api/contracts/editStacks.ts`), strict schemas in `apps/ui/src/api/schemas/editStacks.ts`, the goldens `edit-stacks-*.json` written by `bindings_editlog_stacks_contract_test.go`, the stack methods on `EditLogPort`, and host API 118.

## Consequences

- Un-stacking works after a restart and on a DAW that keeps no take extension data, and the page can show the plan without asking the DAW.
- A stacked passage and the narrator's retry choice survive a new Booth run; both go when the manuscript is replaced, like the other Editing records.
- The record trusts the take list the page sends for its check that a take belongs to the passage: the host does not yet resolve a passage id to its takes. The DAW stacking bindings (SN-D72, [#1199](https://github.com/countrymanprime/narration-utils/issues/1199)) build the plan from host data, so a forged record can only mislabel the narrator's own record, never move audio.
- A stack keeps only the latest record's DAW result; the journal holds each step's result while the session lasts.
- ADR 0147 still governs lane tracks: stacking refuses a fixed-lane track (ADR 0860 point 4), and the app never changes lane mode. Stacking onto lanes, or a different record shape, needs a new ADR that supersedes this one.
