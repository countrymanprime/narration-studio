# 0550. Editing's render source is a second, whole-file scan the narrator picks per chapter, never a silent replacement

**Status:** Proposed (the worker's choices in building the render source; the owner confirms them on #510)
**Date:** 2026-09-28
**Supersedes:** none. It builds on the played-range item source (`apps/desktop/internal/editing/source.go`) and reuses the proofing chapter-to-render association (`internal/proofing`, `RenderStore`/`EvaluateRender`, now closed out into [ADR 0525](0525-proofing-is-met-by-a-current-zero-open-pickup-source-and-every-required-delivery-check-confirmed-through-the-shared-stage-engine.md) and [`docs/architecture/stage-recommendations.md`](../architecture/stage-recommendations.md)) as-is.

## Context

The editing check scans a chapter's unmuted items on their confirmed REAPER track, each within its own played range (`SOFFS`, `LENGTH`, `PLAYRATE`), and compose empty-space candidates across item boundaries. That is analysis of *source* audio: take FX, item gain, fades and REAPER's own repair tools are not applied, so a chore a narrator already fixed downstream of the source (a de-clicker, a gain stage) can still be reported, and a chore hidden by those same tools can be missed.

The chapter's own rendered WAV is added as an explicit second source, so the narrator can check a render without letting it silently replace the item check. Which source counts by default and how the narrator switches was open; the recommendation taken here is: items by default, the narrator picks per chapter, and the evidence always names which source was analyzed.

The chapter-to-render association (which file, its fingerprint, whether it is stale against the chapter's current items) is already built and shipped: `proofing.RenderStore`/`RenderAssociation`/`EvaluateRender`. Duplicating it here would create two disagreeing answers to "is this still the chapter's render."

## Decision

1. **The association is proofing's, reused as-is.** `internal/editing` takes a `*proofing.RenderStore` in its `Config` and calls `proofing.EvaluateRender` to learn the chapter's chosen render, its format and whether it is `current`/`stale`/`missing`/`unsupported`/`none`. Editing writes nothing to `renders.json` and never invents a second "which file" answer.
2. **A second, small store owns only the choice.** `internal/editing/choice.go`'s `ChoiceStore` persists one `SourceChoice` (`"items"` or `"render"`) per chapter, keyed by `documentId`/`chapterId`, mirroring `proofing.RenderStore`'s own sidecar shape (atomic temp-file-then-rename, a newer-version file refused rather than silently reset). Default, when nothing is stored, is `SourceItems`, because editing happens on items. `manuscript.resetDerived` clears its directory the same way it clears `proofing.Dir`, since a re-import renumbers the chapter ids the choice is keyed by.
3. **No played range, no composition, by construction, not by a second algorithm.** `editing.DecodeRender` runs the same windowed analyzers `Decode` does, but with `measure.DiagnosticInput.Range` left `nil` — the whole file, start to finish, exactly the same decoder every other row here already trusts (`internal/measure`, WAV only, bounded by its header checks). The render's silence runs feed the **existing**, already-tested `ComposeEmptySpace` through exactly one synthetic `ItemAudible` spanning the whole file: with one item there is nothing to compose across, so "no composition" falls out of the shape of the input rather than a parallel head/gap/tail implementation that could drift from the item path's own rules.
4. **Ledger scope is the file's own fingerprint, not an item or track scope.** Unlike the per-item records (`ledger.go`, scoped to one `ItemGUID`, currency judged by `evidence.EvaluateFingerprints`), a render-path record (`editing.render`, `render_ledger.go`) is scoped to `{documentId, chapterId}` only and carries the render's fingerprint key (`proofing.RenderFingerprint.Key`) in its JSON payload. Currency is a direct key comparison, `CurrentRenderRecord`, layered on top of (never replacing) `proofing.EvaluateRender`'s own staleness: a render can be the chapter's current association *and* never have been scanned by editing, or scanned once and then re-rendered — two different `unknown` causes, both real.
5. **Every editing signal, from either source, says which one it read.** `EmptySpaceSignal` (items) and `RenderEmptySpaceSignal` (render), and the click/breath `UnvalidatedSignal` calls for both, all carry a `{kind: "source", label: "Source analyzed", value: "items on the chapter's track" | "the rendered file (FX and edits included)"}` evidence entry, unconditionally, whatever the signal's own state — this was not optional for the render choice alone; the item path gained the same entry so the two are symmetric.
6. **Choosing render never starts a scan that would silently disagree with a not-yet-run item check, and vice versa.** The two scans write to separate findings-store scopes (`chapterID` for items, `chapterID + "-render"` for render) so switching source and re-running never overwrites the other source's last candidates; `Finding.Manuscript.ChapterID` still carries the real chapter id on both, and `evidence["source"]` tells them apart on read. A narrator can switch back to items and still see the item path's last-known candidates undisturbed.
7. **Starting a render-choice scan refuses only when there is no association at all.** `proofing.RenderMissing`/`RenderStale`/`RenderUnsupported` are allowed to start (there is a real, named file and a real, specific reason nothing was decoded); only `RenderNone` ("no rendered file") refuses to start, mirroring "an unconfirmed mapping refuses to start" for the item path. This keeps the specific unknown cause visible on the signal rather than hiding it behind a rejected `Start()`.
8. **Click and breath stay unknown for both sources, unconditionally.** The corpus validation that would ever let a click or breath signal reach `met` ([ADR 0510](0510-click-and-breath-signals-open-only-on-a-recorded-permissioned-held-out-run-at-target-in-every-condition.md)) has not run; `validatedAnalyzerVersions` is still empty. The render path's own `RenderClickBreathEvidence` still surfaces a decoded candidate as an evidence entry on the (permanently unknown) signal — "a render with a known click reports it" — without inventing a validated version to make it pass.

## Consequences

- A narrator who has never picked a render for a chapter sees editing's item check exactly as before; nothing about the item path changes behaviour for the default choice. `provider.go`'s `SignalProvider.Signals` gained one read (`sourceChoice`) before it branches, at zero cost when the answer is the default.
- Switching to render mode costs one narrator click and one scan of a whole file (a single 0%→100% job, not per-item progress — there is exactly one file to decode). It never touches `proofing`'s own render association or its UI (`RenderAssociationSection.tsx`, the Proofing page): the same file, the same picker, one more reader.
- The render path's empty-space findings carry no item or take GUID (a render has no items) and their `TimeRange` is the render file's own seconds, not the chapter's project timeline — a deliberate, documented divergence from the item path's shape (`RenderEmptySpaceFinding`, `internal/editing/findings.go`), since there is no timeline mapping for a whole rendered file to have.
- `hostAPIVersion` moved 80→81 for `EditingSourceChoice`/`EditingSetSourceChoice` (`apps/desktop/bindings_editing.go`); no existing binding's shape changed.
- To let a render's own click or breath candidates resolve to `met`, write a new ADR once the corpus validation exists — this one explicitly does not attempt that.
