# Audacity 3 against the adapter: recording, roll, edits, macros, undo, language (A3-T14 to T23, T32)

**Run 2026-10-19. Status: measured in a real Audacity 3.7.7 on Linux (the official AppImage, Ubuntu 24.04, Xvfb, a PulseAudio null sink, a cloud container); not run on a GitHub-hosted runner, and the Windows job (A3-T30) was written and never run.** Question: of what the app asks an Audacity 3 to do while a narrator records and edits, what really works, what does the adapter send that Audacity does not do, and what has to change? This note is the result of tests A3-T14 to A3-T23, A3-T32 and A3-T33 of the [capability matrix](audacity-3-capability-matrix.md#test-plan); the design they run in is [real-Audacity 3 integration testing](real-audacity3-ci-integration.md). Reference facts moved to [Audacity 3.x: what the app relies on](../reference/daw/audacity-3.md#measured-in-audacity-377).

## What was run and what was not

- **Run:** two halves against one pinned Audacity 3.7.7 (SHA-256 `45c4445f…01ef0`), each test on a fresh profile and a fresh Audacity.
  - **Raw tests** (`src/studio/tests/audacity3/real/edits/*.py`, standard library only): a small client written for the test that speaks the pipe protocol directly and shares no code with the Go client, so a row can show what Audacity did even when the Go client or its fake is wrong. Each test writes its steps as JSON and a Markdown summary.
  - **Adapter tests** (`src/studio/desktop/internal/dawport/audacity/real_edits_linux_live_test.go`, build tag `audacityreal`): the shipped adapter, through a FIFO transport the file carries, doing a backup and restore, a roll, a cut, a stack and un-stack, a macro on a range, lowered stretches and repaired clicks, with the audio measured after each.
  - `src/studio/tests/audacity3/real/edits/run.sh` runs both; `.github/workflows/real-audacity3-edits.yml` runs it on `ubuntu-24.04` by manual dispatch, with the results in the job summary and a `results.json` artifact.
- **Not run:**
  - **A3-T30, Windows named pipes.** `src/studio/tests/audacity3/real/edits/windows.ps1` and `.github/workflows/real-audacity3-windows.yml` download the pinned zip (`audacity-win-3.7.7-64bit.zip`, SHA-256 `1d345a48…017d8`, which this session downloaded and hashed: the same value, and `modules/mod-script-pipe.dll` is in it), enable the module in a portable profile, start Audacity twice and run the raw client against `\\.\pipe\ToSrvPipe`. Nothing here can run `Audacity.exe`, so the script has never executed: its first dispatch is its first test.
  - **A3-T33, Audacity 4.** No 4.x asset is pinned: the release assets could not be listed from this session (the GitHub API was out of the session's scope) and a guessed URL answered 404. The test and the `run.sh` branch exist and record a SKIP with that reason until `NU_AUDACITY4_URL` and `NU_AUDACITY4_SHA256` are set.
  - **A3-T31, the owner's pass**, written as a checklist in [the verification pass](../operations/audacity-verification-pass.md#a3-t31-the-owners-pass-on-windows-with-a-real-microphone).
  - **The LibriVox `kara_01` fixture.** The matrix names it for A3-T19; the tests use generated tones whose frequency changes every second (300 + 40 k Hz in second k), which tell a paste in the wrong place from one in the right place and need no download. A speech fixture would add nothing to what these tests assert.
  - **A GitHub-hosted run of anything.** The Linux workflow is added and has not been dispatched; the hosted-runner questions (the two-start enable, `UpdateNoticeShown`) are as open as the CI note left them. This session's container needed a second launch in about one run in six (a pipe that existed and served nothing), which `run.sh` now retries up to three times and records.
  - **Windows audio, a real microphone, the Booth, and everything that needs an ear.**

## Findings

Each finding says what a real 3.7.7 did that the adapter, the fake or the docs said otherwise, and what was done about it. "Fixed" means a failing test first (the fake corrected, then the adapter), and the adapter tests above pass against the real Audacity.

1. **`ApplyMacro` does not exist.** `GetInfo: Type=Commands` lists 93 batch commands and none of them is `ApplyMacro`; Audacity answers `Your batch command of ApplyMacro was not recognized.` Each saved macro is a menu command, `Macro_<name>` with the name's spaces taken out (`Narration Spaced Name` is `Macro_NarrationSpacedName`, `Narration-Test` is `Macro_Narration-Test`), listed by `GetInfo: Type=Menus` and run as `Macro_<name>:`. It runs on the selected tracks and adds one undo point whatever its steps; with no track selected it opens a modal box and holds the pipe; a missing name fails at once with no dialog. *Fixed:* `Client.ApplyMacro` sends the menu command and `CheckMacroName` refuses an id it cannot know (anything but letters, digits, spaces, hyphens and underscores) before the first command of an edit. *Both the effect on a range and the mastering macro render were affected.* (A3-T20, A3-T20g)
2. **`SetTrackStatus` and `SetTrackAudio` take no `Track`.** Audacity ignores a `Track=` parameter without an error and acts on the selected track. The old stack muted the chapter track after its `Split` and `Delete`, not the take tracks (the chapter was selected last), and named tracks only by luck of a new track being selected. *Fixed:* `SetTrackName` and a new `SetTrackMute` select the track first; `TrackInfo` gains `Muted`. (A3-T17, A3-T19, A3-T18g)
3. **Closing a gap with a `Delete` after a `SplitDelete` does not close it.** With Sync-Lock off, which is how a fresh Audacity starts, the track stayed at 12 s and the "closed" stretch was a silent gap. A plain `Delete` closes up. Further, a `Delete` inside one clip of a track already split into clips moves only that clip's audio and leaves the clips after it where they were, unless the preference `/GUI/EditClipCanMove` ("Editing a clip can move other clips") is 1; it reads as not set on a fresh profile and behaves as 0, and `SetPreference` with `Reload=1` applies it at once. A stack's `Split` then `Delete` left the chapter at its full length until it was on. *Fixed:* a close-up cut is one `Delete`; the close-up cut, the stack and the un-stack turn the preference on for their own commands and put it back (also when the edit fails), through a one-name allow list in the client (threat-model row 14i). (A3-T18, A3-T18g)
4. **Sync-Lock can only be toggled by the `SyncLock` menu command.** `SetPreference` of `/GUI/SyncLockTracks` is stored and ignored by the open project; the preference mirrors the state after a toggle and is absent on a fresh profile. With it off, labels do not move with a close-up cut and drift by its length (a label at 5.2 s was still at 5.2 s after 1 s was cut before it); with it on they move up with the audio. The app's chapter and line labels are therefore wrong after any close-up cut unless Sync-Lock is on. *Recorded, not fixed:* turning Sync-Lock on at link time, or re-stamping labels after a cut, is a feature of its own (N7 in the matrix). (A3-T18)
5. **Undo points are not what the adapter reported.** Measured per command: `Split`, `SplitDelete`, `Delete`, `Paste`, `NewMonoTrack`, `AddLabel`, `SetEnvelope`, `RemoveTracks`, `Import2` and a macro add one each. **`Amplify`, `ClickRemoval`, `Silence`, `SetTrackStatus` and `SetTrackAudio` add none**: the next `Undo` takes back the edit before it, and the effect goes with it. A roll adds one when its recording stops. *Fixed:* a close-up cut reports 1 (was 2), a stack 4 (was 5), lowered stretches 0 (were 1 each), repaired clicks 0 (were 1 each). (A3-T22c, A3-T16, A3-T16g, A3-T18g)
6. **`Undo` with nothing to undo opens a modal "Nothing to undo" box (no title bar) and holds the pipe.** In two hand probes, before the box was answered, Audacity then crashed with a crash report window; the test did not reproduce the crash. Scripting has no undo depth, so the app may only send an `Undo` it can prove has an edit behind it. *Recorded.* (A3-T22b)
7. **A batch command ends a recording.** Sent during a recording, `Message`, `GetInfo` (any type), `SelectTime` and `SetLabel` end it: the clip stops at that moment, the status bar reads Stopped within a second, and the audio so far is kept. The menu commands `AddLabelPlaying`, `SelectNone` and `Stop` do not. The matrix's 1 s `Message` heartbeat would end every take, and a stop made in Audacity's own window cannot be seen, because nothing readable can be sent while a take runs. *Recorded; the design consequence is for the Booth:* after a record or a roll starts, the app sends only `AddLabelPlaying` and `Stop` until the narrator stops, and shows its own state. (A3-T15)
8. **A recording starts late.** Capture began 1.5 to 2.1 s after the reply to `Record1stChoice` on this null sink, so a clock started at the reply overshoots by that much; `AddLabelPlaying` put its label at the true position within 0.25 s of the audio. The latency is the device's, measured, not asserted against a number. (A3-T14)
9. **Where a recording lands, and the sample-rate box.** With a mono 44.1 kHz track selected and the stereo input, `Record1stChoice` made a new stereo track at the cursor; with a stereo 44.1 kHz track selected it appended to it; with a 22.05 kHz track in a 44.1 kHz project it opened "Too few tracks are selected for recording at this sample rate" (title "Too Few Compatible Tracks Selected"), which holds the pipe until OK is clicked and then answers at once. `GetInfo` reports no per-track rate, so the adapter cannot guard the case before sending. *Recorded.* (A3-T14)
10. **`PunchAndRoll` works as the matrix hoped.** With the cursor at the roll point and `/AudioIO/PreRoll` set to 1 s, the earlier audio was sample-for-sample unchanged, the new recording began at exactly the roll point (an 880 Hz signal over a 440 Hz take: 872 to 880 Hz from the first window), the clip was split there, one `Undo` after the recording stopped took the whole roll back, and through the adapter the backup, the roll and the undo agreed. `GetPreference` of `/AudioIO/PreRoll` fails until the key has been set once. (A3-T16, A3-T16g)
11. **Gain: `Amplify` is exact and steps; the envelope ramps.** `Amplify` with a ratio for 6 dB gave 6.00 dB, outside the selection untouched, and a step at each edge about 8 times the tone's own largest sample-to-sample jump (measured at a crest). Envelope points set with `SetEnvelope` 10 ms either side gave the same 6.00 dB, a ramp (edge jump 0.019 against 0.25), were applied by `Export2`, and add one undo point. *Recorded:* the envelope route is better on every count measured and is not built; changing `ReduceRangeGain` to use it is a design change for the lowered-stretches capability. (A3-T21)
12. **`ClickRemoval` with its defaults repairs a narrow spike and stalls on anything else.** An 8-sample full-height spike over a quiet tone went from 0.90 to 0.10 at the peak. A 3 ms click (132 samples, wider than the effect's 20-sample width) opened the modal "Algorithm not effective on this audio. Nothing changed." and held the pipe; the adapter's `RepairClick` timed out after 5 s with the box still open, and a click on OK freed the pipe. The adapter cannot tell this box from a slow effect. *Recorded.* (A3-T21, A3-T21g)
13. **Backups work.** `BackupAround` cloned 30 to 270 s of a 300 s track to a muted track holding exactly that window (`Paste` starts at the cursor, not at 0); after `Silence` over 100 to 200 s, `RestoreBackup` made the 30 to 270 s export sample-for-sample the original; a stereo source got a stereo backup; a deleted backup track was refused as stale with nothing changed. (A3-T17)
14. **Export.** `Export2` wrote only the selected, unmuted tracks: with the audio track selected 2.00 s; with only the label track or no track selected it answered OK and wrote no samples; `NumChannels` 1 and 2 gave 1 and 2 channels; a path with spaces, a non-ASCII name and about 330 characters all worked. The default is 16-bit PCM at the project rate, and none of the format keys tried changed it, so the bit depth of a delivery file is not settable by a pipe command found so far. Exports are dithered by default, so two exports of recorded audio differ; `/Quality/DitherAlgorithmChoice` and `/Quality/HQDitherAlgorithmChoice` with the words `None`, `Rectangle`, `Triangle`, `Shaped` and `Reload=1` fix that, while the numeric `DitherAlgorithm` keys are written by Audacity and not read. *Recorded.* (A3-T23)
15. **The German interface.** Every batch and menu id the adapter sends is unchanged, `BatchCommand finished: OK` and `Failed!` stay English (the failure text is German), the menu labels are German, a name the app sets is kept, and the default label track name is translated (`Textmarken 1` for `Labels 1`) while the default audio track name is not (`Audio 1`). A plug-in command's id in `GetInfo: Type=Commands` can be translated and hold a raw newline, which is not valid JSON: the Go client's `repairJSON` handles a raw control character in a string, and the raw client needed the same. The app must find its label track by the name it gave it. (A3-T32)
16. **Smaller facts.** `GetInfo: Type=Preferences Format=JSON` got no reply and Audacity crashed once in a hand probe; it is not used. `GetPreference` fails for a key nothing has set. The first start on a fresh profile followed by a second start worked each time here; the killed first start leaves a project that the second start offers to recover in a modal dialog unless the temp folder is cleared between starts, and `run.sh` clears it. `Paste` at a cursor inserts and moves what follows within the clip. A macro, `Amplify` and the other effects need a selected track.

## What changed in the repository

- **`audacitybridge`:** `ApplyMacro` sends `Macro_<name>`; `CheckMacroName`; `SetTrackName` and `SetTrackMute` select first; `Preference`, `SetPreference` (one allowed name) and `PrefClipsMove`; `TrackInfo.Muted`. The fake models selection-based track commands, macros as menu commands, mute, and a preference store.
- **`dawport/audacity`:** a close-up cut is one `Delete`; `clipsMove` wraps the close-up cut, the stack and the un-stack; undo counts for a cut, a stack, lowered stretches and repaired clicks; the macro name is checked before any edit; the edit fakes model `Delete` over a gap and macros as menu commands. Each change has a test that failed before it.
- **Docs:** the reference page, the capability sections that cite these commands, threat-model rows 14f, 14h and the new 14i, and the [verification pass](../operations/audacity-verification-pass.md) (corrected Part C expectations and the A3-T31 checklist).

## Capability levels

No capability is promoted. The rule for this work was to promote on a passing real run and otherwise leave Experimental with the reason; the adapter tests passed against a real Audacity here, but only on Linux, in a container, never on a hosted runner and never on the platform the app ships on, and `docs/architecture/daw-integration.md` keeps every Audacity capability Experimental until the owner's pass. The reasons per capability: `punch`, `cut_range`, `stack_takes`, `fx_range`, `backups` pass their adapter tests on Linux and wait for Windows (A3-T30, A3-T31); `range_gain` and `click_repair` pass but report 0 undo points and one can stall on a modal box; `macro_render` was not run (it needs the Windows path seam); `record` and `undo_last` are not built.

## Not proven

- Anything on Windows: the reply bytes, `Command.Path`, whether Sync-Lock and `EditClipCanMove` start the same, the dialogs of the first run, the paths of A3-T23, and every number measured on the null sink (the capture latency above all).
- That the hosted `ubuntu-24.04` runner behaves as this container did: the two-start enable, the retry rate, and the recording latency.
- The crash after the "Nothing to undo" box, the crash on `GetInfo: Type=Preferences`, and why a launch occasionally came up with a pipe that served nothing.
- Whether a macro id for a name with other characters (an accent, a punctuation mark) exists; the client refuses them.
- Whether `Record2ndChoice`, `TimerRecord` or `TogglePlayRegion` do anything useful when scripted; none was run.
